Focused correction
------------------
1. Before AnswerService/retriever startup, Technical QA creates a run-specific isolated copy of the production Qdrant payload.
2. The production qdrant/.lock is never copied, deleted, modified, or opened through Qdrant by the QA preparation step.
3. Each .sqlite database is cloned with Python sqlite3 backup from a read-only source connection, producing a consistent QA snapshot even when the production DB is open.
4. SQLite runtime sidecars (-wal, -shm, -journal) and qdrant/.lock are excluded from the QA copy.
5. config.settings.QDRANT_DIR is redirected inside the QA process to the isolated snapshot before AnswerService imports.
6. The existing v6.4.66 one-process/shared-service architecture and fresh per-case ChatManager reset remain in place.
7. Per-case evidence and result ZIP format remain; summary records Harness=single_process_isolated_qdrant and Qdrant=readonly_sqlite_snapshot.
8. The temporary QA snapshot is removed on best effort after the result ZIP is created.

Why this is the correct layer
-----------------------------
The v6.4.66 office rerun proved that process churn was no longer the cause: the single shared QA process still failed only when OC-011 reached the first full embedding/vector path. Isolating certification reads from the live embedded-Qdrant directory removes external runtime lock contention without changing production retrieval behavior or mutating the production store.
