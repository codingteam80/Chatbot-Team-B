DocuBot v6.5.3.1 - KB Update Worker Lock Handoff + Latency Decision Diagnostics
================================================================================

PURPOSE
-------
Hotfix the field-observed Update Knowledge Base self-lock where the live Streamlit
parent PID was recorded as the update-lock owner and the child worker immediately
blocked itself. Preserve the validated v6.5.3 answer/retrieval behavior while
adding explicit latency decision evidence for single-query vs MultiQuery paths.

RUNTIME FIXES
-------------
1. Only the isolated KB update worker owns logs/kb_update/kb_update.lock.
2. The launcher never acquires the cross-process worker lock.
3. A legacy v6.5.3 parent/self lock is removed only when:
   - lock PID equals the current launcher PID,
   - lock source equals the current launch source, and
   - owner_role is absent/legacy launcher metadata.
4. A real live worker lock remains blocking.
5. Dead/stale worker locks are cleared safely.
6. New locks include worker role, run_id, parent_pid, project_root, and a
   process-start identity token to reduce PID-reuse false positives.
7. Streamlit adds a browser-session update_in_progress guard against repeated
   button activation while one update is being launched/run.
8. The portability dry-run reproduces the legacy self-lock on a TEMPORARY lock
   file; it never calls smart_build and never rebuilds Qdrant/BM25.

LATENCY HARDENING / OBSERVABILITY
--------------------------------
The v6.5.3 single-query semantic+BGE early-accept and prewarm behavior are
preserved exactly. This hotfix does NOT change acceptance thresholds.
The semantic resolver orchestration now records:
- resolver readiness time,
- original single-query resolution time,
- MultiQuery variant-generation time,
- widened semantic-resolution time,
- total Rule-resolution time,
- whether MultiQuery was skipped because the original query was proven,
  or used because the original query remained ambiguous.

This gives a direct trace for the remaining latency goal without weakening
precision or adding phrase-to-Rule mappings.

FIELD RETEST AFTER INSTALL
--------------------------
1. Close DocuBot/Streamlit before applying the patch.
2. Apply v6.5.3.1 and confirm installer PASS.
3. Start DocuBot locally.
4. If source changes are detected, confirm the warning and click Update
   Knowledge Base ONCE.
5. Expected lock flow:
      launcher -> handoff check -> worker owns lock -> preflight -> build ->
      semantic Rule index verification -> KB Health -> PASS -> lock released.
6. If a different live worker already owns the lock, the second update must
   remain BLOCKED instead of stealing the lock.
7. After KB-button verification, run retrieval-only diagnostics or the mixed
   benchmark and inspect MISRA SEMANTIC LATENCY DECISION events.
